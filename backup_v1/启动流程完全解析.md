## 一、总览：启动阶段全景图

程序启动被设计为 **"先出界面、后补数据"** 的异步策略，整体分为 6 大阶段：

| 阶段 | 颜色标记 | 核心任务 | 所在方法 |
|------|----------|----------|----------|
| **Phase 0** | ⚫ 入口 | 创建 Tk 根窗口与 App 实例 | `main()` |
| **Phase A** | 🔴 初始化 | 加载配置、调试器、播放器 | `ImageBrowserApp.__init__` |
| **Phase B** | 🟢 绘界面 | 绘制所有 UI 控件并显示窗口 | `_create_ui()` / `_create_browser_ui()` |
| **Phase C** | 🟡 延迟启动 | 调度后台线程，避免阻塞主界面 | `_post_ui_startup()` |
| **Phase D** | 🔵 定目标 | 读取缓存、确定上次打开的书签与文件夹 | `_optimized_startup_v2()` |
| **Phase E** | 🟣 填内容 | 异步加载树状图、图库、数据库、标签 | `_async_build_tree()` / `_async_load_gallery_startup()` |
| **Phase F** | ⚪ 数据库 | 连接 SQLite、同步数据、刷新标识 | `_async_init_database_and_merge()` |

## 二、详细执行步骤

### Phase 0：程序入口 ⚫

**位置**：`main.py` 底部

```python
def main():
    root = tk.Tk()                    # 创建 Tkinter 根窗口
    app = ImageBrowserApp(root)       # ⭐ 进入核心初始化
    root.protocol("WM_DELETE_WINDOW", app._on_closing)

```

**效果**：此时仅有一个空的 Tk 窗口被系统创建，所有业务逻辑尚未开始。

### Phase C：延迟启动调度 🟡

**位置**：`self.root.after(10, self._post_ui_startup)`

#### 步骤 C1：`_post_ui_startup()`

```python
def _post_ui_startup(self):
    # [C02] 后台线程：初始化文件夹缓存管理器
    threading.Thread(target=self._init_folder_cache_async, daemon=True).start()

    # [C03] 10ms 后执行：进入优化启动流程 V2
    self.root.after(10, self._optimized_startup_v2)
```

> ⚠️ **注意**：这里使用 `after(10)` 而非立即执行，是为了让 Tkinter 主循环先处理完窗口绘制事件，避免启动逻辑与 UI 刷新争抢主线程。

### Phase D：确定启动目标 🔵

**位置**：`_optimized_startup_v2()`

#### 步骤 D1：读取 UI 缓存

```python
self._startup_cache = self._load_ui_cache()
```

**实现**：从 `config.json` 的 `ui_cache` 字段读取：
- `last_folder`：上次浏览的文件夹
- `last_scroll_y`：图库滚动位置
- `tree_scroll_position`：树状图滚动位置

#### 步骤 D2：确定启动目标 `_get_startup_target()`

```python
target_bm, target_folder, final_target = self._get_startup_target(last_folder)
```

| 返回值 | 含义 |
|--------|------|
| `target_bm` | 上次使用的书签字典（含 `path`, `id`, `display_name`） |
| `target_folder` | 该书签下保存的 `last_folder` |
| `final_target` | 最终要打开并选中的文件夹路径 |

**内部逻辑**：
1. 遍历 `self.config.devices[本机ID].bookmarks`
2. 匹配 `last_folder` 属于哪个书签路径前缀
3. 读取该书签的 `bookmark_states` 获取详细状态
4. 对网络路径使用 `_quick_path_check()`（ping 主机 300ms 超时，避免 `os.path.exists` 阻塞）

#### 步骤 D3：保存当前上下文

```python
self.current_root = os.path.normpath(target_bm['path'])
self.current_folder = final_target
self._current_bookmark_id = target_bm['id']
```

### Phase E：异步填充内容 🟣

这是**真正的数据加载阶段**，采用**多线程并行**策略。

#### 步骤 E1：异步构建树状图 `_async_build_tree()`

```python
threading.Thread(
    target=self._async_build_tree,
    args=(self.current_root, target_bm, final_target, self._startup_cache),
    daemon=True
).start()
```

**线程内执行**：

```text
_async_build_tree(root_path, target_bm, final_target, startup_cache)
├── 尝试 _load_tree_cache(root_path)      # 读 \data\tree_设备名_哈希.json
│   └── 若命中且有效 → 回到主线程调用 _on_tree_loaded(from_cache=True)
│
└── 若无缓存或失效
    ├── _scan_folder_recursive(root_path)  # 递归 os.scandir 扫描所有子文件夹
    └── 回到主线程调用 _on_tree_loaded(from_cache=False, entries=nodes)
```

**`_on_tree_loaded`（主线程回调）**：

```python
def _on_tree_loaded(self, root_path, target_bm, final_target, startup_cache, 
                    from_cache=False, entries=None, cache_data=None):
    # 1. 调用 TreeExplorer.startup_load() 一次性构建完整树
    self.tree_explorer.startup_load(
        root_path, 
        cache_data=cache_data,      # 若从缓存加载
        entries=entries,            # 若从扫描加载
        selected_path=final_target,
        scroll_position=startup_cache.get('tree_scroll_position', 0.0)
    )

    # 2. 继续后续启动流程
    self._continue_startup_after_tree(target_bm, final_target, startup_cache)

    # 3. 延迟 2 秒后保存树缓存（供下次启动使用）
    self.root.after(2000, self.tree_explorer.save_current_tree_cache)
```

**`TreeExplorer.startup_load()` 效果**：
- 清空旧树
- 插入根节点
- **从缓存递归构建所有层级**（`_build_tree_from_cache`），而非只建一级
- 恢复上次选中的文件夹路径（调用 `restore_state`）
- 若路径有效，展开其父级路径并选中节点

#### 步骤 E2：异步加载图库（与树并行）

```python
threading.Thread(
    target=self._async_load_gallery_startup,
    args=(final_target, self._startup_cache.get('last_scroll_y', 0)),
    daemon=True
).start()
```

**线程内执行**：

```python
def _async_load_gallery_startup(self, folder_path, scroll_y=None):
    # 确保 folder_cache 存在
    if not hasattr(self, 'folder_cache'):
        self.folder_cache = FolderCacheManager(self.debug)

    # ⭐ 关键：启动时绝不强制数据库同步，优先用 JSON 缓存快速显示
    self._load_gallery_unified(
        folder_path, scroll_y,
        force_db_sync=False,        # 启动专用：不清缓存，避免重新扫描
        source="启动加载",
        include_subfolders=False    # 启动时跳过子文件夹宫格，加速
    )
```

**`_load_gallery_unified()` 调用链**：

```text
_load_gallery_unified(folder_path, scroll_y, force_db_sync, source, include_subfolders)
└── gallery_loader.load_folder_unified(
        folder_path, 
        self.gallery,           # GalleryViewer 实例
        self._update_status,    # 状态栏回调
        scroll_y,
        db_ready=self._db_ready,    # 此时通常为 False
        force_reload=force_db_sync,
        source=source,
        on_loaded=lambda path, count: self._on_gallery_loaded(path),
        tree_state=...,
        include_subfolders=include_subfolders
    )
```

**`GalleryLoader.load_folder_unified()` 效果**：
1. 检查 `_last_loaded_folder` 避免重复加载
2. 在**后台线程**执行 `_do_scan()`：
   - 调用 `_scan_folder_new()` 扫描文件夹内视频/图片
   - 按规则匹配缩略图（单图单视频、多图单视频、多图多视频宫格等）
   - 若 `db_ready=True`，查询数据库注入采集信息（番号、演员、时长）
3. 回到**主线程** `after(0, _update_ui)`：
   - 调用 `gallery.load_items_new()` 批量渲染缩略图
   - 恢复滚动位置 `scroll_y`
   - 触发 `_on_gallery_loaded` 回调

> 🔴 **重要**：此时数据库通常**尚未就绪**，所以图库首次加载是**纯文件系统模式**，不显示数据库中的番号/演员信息。这些信息会在数据库就绪后通过 `_incremental_refresh_gallery` 补全。

#### 步骤 E3：树加载完成后续动作 `_continue_startup_after_tree()`

在 `_on_tree_loaded` 末尾调用，启动**三个后台线程**：

```text
_continue_startup_after_tree(target_bm, final_target, startup_cache)
├── [E02] 线程: _async_restore_bookmark_state(target_bm)
│   └── 调用 bookmark_manager.restore_last_bookmark(bm_id, trigger_callback=False)
│       # 静默选中书签节点，不触发 on_select（避免重复加载树和图库）
│
├── [E03] 线程: _async_load_video_tags()
│   └── 读取 config.tags_v2 → 统计标签使用次数 → 主线程刷新标签超链接区域
│
└── [E04] 线程: _async_init_database_and_merge(final_target)
    └── 数据库初始化与数据合并（见 Phase F）
```

### Phase F：数据库初始化与增量刷新 ⚪

**位置**：`_async_init_database_and_merge()`

#### 步骤 F1：数据库连接

```python
from init_database import ensure_database_ready
db_success, db_msg = ensure_database_ready()   # 建表/升级表结构

self.db = DatabaseManager(debug_utils=self.debug, fast_mode=True)
```

| 参数 | 说明 |
|------|------|
| `fast_mode=True` | 跳过重复结构检查，大幅提升启动速度 |

**效果**：`self.db._cache` 内建立内存字典（`folders`, `files`, `actors`, `code_index` 等），但**缓存数据是后台异步加载**的。

#### 步骤 F2：标记已同步视频

```python
self._mark_synced_videos()
```

**实现**：委托给 `GalleryViewer.rebuild_synced_set()`：
- 遍历数据库缓存中所有视频文件
- 若存在 `video_title` / `video_code` / `duration` / `release_date` 任一字段，或有关联演员，则视为"已联网同步"
- 路径存入 `gallery._synced_video_paths` 集合

#### 步骤 F3：延迟合并扫描数据

```python
# 延迟 5 秒执行，确保 UI 完全加载且扫描数据已准备好
self.root.after(5000, delayed_merge)
```

**`delayed_merge` 内部**：

```python
self.db.merge_folder_scan_data(
    folder_path, 
    self._folder_scanned_data,      # 启动时文件夹扫描的原始结果
    device_id=self.config.device_id,
    bookmark_id=self._current_bookmark_id,
    debug=self.debug
)
```

**效果**：将文件系统扫描到的文件信息（大小、修改时间）与数据库记录对比，批量 `INSERT` 或 `UPDATE`，然后**异步刷新内存缓存**。

#### 步骤 F4：数据库就绪后 UI 更新

```python
self._on_db_ui_update()   # 主线程执行
```

**关键动作**：

1. 更新各组件的数据库引用：
   ```python
   self.bookmark_manager.db = self.db
   self.tree_explorer.db = self.db
   self.gallery.db = self.db
   ```

2. 初始化 `RelationManager` 和 `GalleryLoader`（若尚未创建）

3. 刷新标签超链接 `_refresh_tag_links()`

4. **委托 GalleryViewer 刷新图库**：
   ```python
   self.gallery.on_db_ready(self.db)
   ```
   这会触发：
   - `rebuild_synced_set()` → 更新缩略图上的 🔗 同步标识
   - `_update_synced_indicators()` → 显示/隐藏左上角同步角标
   - `_load_video_info_async()` → 为每个视频缩略图异步加载演员、时长、标题

#### 步骤 F5：启动完成

```python
self._on_startup_complete()
```

**效果**：
- 计算总耗时 `time.time() - self._start_time`
- 状态栏显示 `就绪 (总用时: x.xx s)`
- 初始化 `CrawlerInterface`（爬虫接口）
- 若调试模式开启，2 秒后自动运行 `run_data_integrity_check()`（数据完整性自检）

## 五、线程协作模型

```
主线程 (Tkinter 事件循环)
    │
    ├── 绘制 UI (Phase B)
    ├── after(10) → _post_ui_startup
    │       │
    │       └── 启动线程1: _init_folder_cache_async (FolderCacheManager)
    │       └── after(10) → _optimized_startup_v2
    │               │
    │               ├── 启动线程2: _async_build_tree (TreeExplorer)
    │               │       └── 完成后: root.after(0, _on_tree_loaded)
    │               │
    │               └── 启动线程3: _async_load_gallery_startup (GalleryLoader)
    │                       └── 扫描完成后: gallery.after(0, _update_ui)
    │
    └── 线程4 (由 _continue_startup_after_tree 启动):
            _async_init_database_and_merge
            └── 完成后: root.after(0, _on_db_ui_update)
                    └── gallery.on_db_ready(self.db)  [增量刷新标识]
```

> ⚠️ **线程安全要点**：
> - `GalleryLoader` 使用 `self._gallery_load_lock` 防止重复加载
> - `DatabaseManager` 使用 `threading.local()` 实现**线程专属 SQLite 连接**
> - `GalleryViewer` 的所有 UI 更新必须通过 `self.parent.after(0, ...)` 抛回主线程

## 六、设计模式与优化建议

### 6.1 当前架构的优点

1. **延迟加载（Lazy Loading）**：数据库、子文件夹宫格、爬虫配置均在首次需要时才初始化
2. **缓存分层**：树缓存 → 文件夹缓存 → 数据库缓存 → 内存缓存，四级加速
3. **线程隔离**：所有 IO 阻塞操作（文件扫描、数据库查询）均放在后台线程

### 6.2 可优化的痛点

| 痛点 | 现状 | 优化方向 |
|------|------|----------|
| **启动时序复杂** | `__init__` 内嵌套了 5 层 after + 4 个线程，回调链过长 | 引入**状态机**（`StartupStateMachine`），用 `Enum` 定义阶段，每个阶段完成后触发下一个，避免回调地狱 |
| **UI 与逻辑耦合** | `main.py` 长达 4000+ 行，既管窗口又管数据库同步 | 引入 **MVP / MVVM** 模式：`AppController` 持有 `View` 与 `Service`，`main.py` 只负责组装 |
| **GalleryLoader 职责过重** | 既扫描文件系统，又查询数据库，又匹配缩略图规则 | 拆分为 `FolderScanner`（纯 IO）、`ThumbnailMatcher`（纯逻辑）、`GalleryPresenter`（纯 UI 绑定） |
| **路径处理不一致** | 部分方法用 `os.path.normpath`，部分用 `.lower()`，部分两者都用 | 统一封装 `Path.normalize()` 单例，所有路径比较走同一函数 |
| **数据库缓存刷新粗暴** | `_load_all_to_cache()` 全量重建字典，数据量大时卡顿 | 改为**增量更新**：`merge_folder_scan_data` 后直接 patch 内存字典，而非触发全量 reload |

### 6.3 重构示例：状态机化启动流程

```python
from enum import Enum, auto

class StartupPhase(Enum):
    INIT_CONFIG = auto()
    UI_CREATED = auto()
    TREE_LOADED = auto()
    GALLERY_SHOWN = auto()
    DB_READY = auto()
    COMPLETE = auto()

class StartupStateMachine:
    def __init__(self, app):
        self.app = app
        self.phase = StartupPhase.INIT_CONFIG

    def transition_to(self, next_phase):
        self.phase = next_phase
        # 每个阶段只关心自己的入口，不再嵌套 after()
        handlers = {
            StartupPhase.UI_CREATED: self.app._post_ui_startup,
            StartupPhase.TREE_LOADED: self.app._on_tree_loaded,
            StartupPhase.DB_READY: self.app._on_db_ui_update,
        }
        handler = handlers.get(next_phase)
        if handler:
            handler()
```

## 七、总结：一条时间线看懂启动

```
0ms      python main.py
    └── ImageBrowserApp.__init__
        ├── [A] 加载配置、调试器、播放器（<100ms）
        ├── [B] 绘制窗口、书签树、资源管理器、图库、日志（~200ms）
        └── 窗口显示 ✅

~200ms   _post_ui_startup
    ├── 线程1: 初始化文件夹缓存管理器
    └── after(10) → _optimized_startup_v2
        ├── 线程2: 异步构建树（读缓存或扫描）
        └── 线程3: 异步加载图库（读 JSON 缓存或扫描）

~300ms   树构建完成 → _on_tree_loaded
    ├── TreeExplorer.startup_load(选中上次文件夹)
    └── 启动线程4: 数据库初始化

~500ms   图库渲染完成（纯文件系统数据）
    └── 用户已能看到缩略图 ✅

~3000ms  数据库连接成功 → _on_db_ui_update
    ├── 注入番号、演员、时长到缩略图
    └── 显示 🔗 同步角标 ✅

~8000ms  延迟合并完成（merge_folder_scan_data）
    └── 数据库与文件系统差异同步完成 ✅
```

> 📌 **给学习者的建议**：若要重写优化，建议先从 `TreeExplorer` 和 `GalleryLoader` 入手，将它们的**缓存逻辑**和**扫描逻辑**彻底解耦，再引入上述状态机统一管理启动时序。主线程只保留 UI 事件绑定，所有数据操作通过 `Service` 层 + 回调接口与 UI 通信。
